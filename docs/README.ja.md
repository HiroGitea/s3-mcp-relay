# S3 MCP Relay

**S3 互換オブジェクトストレージを介して、直接接続できない Linux ホストを安全に運用します。**

インバウンドポート、VPN、踏み台、双方向の直接経路は不要です。
エンドツーエンド暗号化により、オブジェクトストレージは一時的な暗号文の転送に限定されます。

両端は同じバケットへ**アウトバウンドのみ**の HTTPS リクエストを送信します。コントローラーと隔離ホストの間に直接接続は必要ありません。

## 概要

一部の環境では、承認済みオブジェクトストレージへのアクセスを許可する一方で、すべてのインバウンド接続を禁止しています。この場合、VPN、踏み台、SSH ポートの公開といった一般的な手段は利用できないか、既存のセキュリティポリシーに反します。

S3 MCP Relay は、承認済みのアウトバウンド経路を限定的なコントロールプレーンとして使用します。コントローラーとリモートエージェントは、専用バケットまたは prefix を介して認証済み暗号文を交換します。

## 主な機能

| 機能 | 説明 |
|---|---|
| **プログラム実行** | 短いコマンドは `exec`、数時間かかる処理は `start_job` |
| **ファイル転送** | 小さいものはインライン、大きいものはバケット経由で**会話を通さず** |
| **パス管理** | 読み取り、書き込み、一覧、作成、削除、移動 |
| **状態報告** | ハートビート、直近のエラー、ジョブ結果、マシン指標——尋ねなくても見える |

## セキュリティモデル

- **エンドツーエンド暗号化。** すべてのオブジェクトを XChaCha20-Poly1305 で暗号化し、S3 のキーを AAD として認証します。正当な暗号文でも別のエージェントのメールボックスへ移して再生することはできません。ストレージ事業者に見えるのは暗号文だけです——サーバーサイド暗号化が守るのはディスクであって、サービス自身からは守りません。
- **HTTPS 強制。** 平文エンドポイントは、ローカルテスト用に明示的に許可しない限り拒否されます。
- **一時的な転送。** 正常に読み取られたオブジェクトは削除されます。バケットは履歴保管ではなく転送層として設計されています。
- **エージェントごとの分離。** それぞれが自分の認証情報と、自分の prefix に限定された IAM ポリシーを持ちます。
- **構造的な制限。** コマンドの有効期限、プロトコルのバージョン検証、実行タイムアウト、出力上限、パスの限定、そして認証情報を子プロセスへ渡すことを拒否する環境変数の許可リスト。

### 2 つの権限モード

**制限モード**（既定）：`exec` は許可リストに完全一致する絶対パスのみを実行し、シェルを介しません。ファイル操作は宣言されたルート内に限定されます。

> [!WARNING]
> **フル機能モード**（`allow_any_path` + `allow_any_program`）は、ローカルシェル相当のリモートコード実行機能を意図的に提供します。バケット、コントローラー、エージェント、MCP セッションが同一の信頼された管理境界に属する場合に限り有効化し、共有ホストでは使用しないでください。

## クイックスタート

### 要件

| 項目 | 最小要件 |
|---|---|
| Rust ツールチェーン | Rust 1.94 以降 |
| オブジェクトストレージ | 専用バケットまたは prefix を持つ S3 互換エンドポイント |
| リモートホスト | systemd または OpenRC を使用する Linux |
| MCP クライアントホスト | Claude Code や Codex など、ローカル MCP をサポートするクライアント |

### 1. ビルド

```bash
cargo build --release --workspace
```

### 2. エージェントのインストール

```bash
sudo sh deploy/install-agent.sh \
  --agent-id legacy-01 \
  --endpoint https://cn-sy1.rains3.com \
  --bucket my-relay-bucket \
  --access-key AK... --secret-key SK...
```

systemd と OpenRC を自動判別し、`0600` の設定ファイルを書き、共有鍵を生成して一度だけ表示します。

### 3. コントローラーのインストール

```bash
sh deploy/install-controller.sh \
  --agents legacy-01 \
  --endpoint https://cn-sy1.rains3.com \
  --bucket my-relay-bucket \
  --access-key AK... --secret-key SK... \
  --shared-key <手順 2 で表示された鍵>
```

コントローラーはユーザースコープにインストールされ、root は不要です。`claude` CLI が利用可能な場合、インストーラーは MCP サーバーを自動登録できます。

### 4. 接続の確認

MCP クライアントを再起動し、`list_agents` を呼び出します。

## ツール一覧

| ツール | 説明 |
|---|---|
| `list_agents` | 稼働中のエージェント、ジョブ、直近のエラー、マシン指標 |
| `ping` | 疎通確認 |
| `exec` | 単一プログラム、シェルなし、引数は展開されない |
| `start_job` · `list_jobs` · `job_output` · `cancel_job` | 分離実行される長時間処理 |
| `read_file` · `write_file` | 1 MiB 以下。内容は会話を通る |
| `push_file` · `pull_file` | サイズ無制限。バケット経由でストリーミング |
| `list_dir` · `make_dir` · `remove` · `move_path` | パス管理 |

### ツールの選択

> [!IMPORTANT]
> `exec` は短時間で完了するコマンドに限定してください。コントローラー側でタイムアウトしても、リモートプロセスが監視されないまま継続する場合があります。ビルド、学習、インポートなど数分以上かかる可能性がある処理には `start_job` を使用します。

`read_file` は内容をツール結果として返すため、モデルのコンテキストに載ります——100 KB でおよそ 4 万トークンです。数十 KB を超えるなら `pull_file` を使ってください。

## 長時間ジョブ

`start_job` はジョブ ID を即座に返し、既定で最大 6 時間そのプロセスを監督します。出力はエージェント上のファイルへ直接流れるため、数 GB の学習ログでもどちら側のメモリも消費しません。

**ジョブ完了はモデルへ自動送信されません。** これは MCP の対話モデルに由来する性質であり、実装上の欠陥ではありません。エージェントは結果をハートビートに含め、コントローラーは 30 秒ごとにローカル状態ファイルを更新します。結果は `list_jobs`、`/relay-status`、またはステータスラインから確認できます。

## ファイル転送

```
push_file(agent_id="legacy-01",
          local_path="~/torch-2.4.0-cp311-linux_x86_64.whl",
          remote_path="/srv/app/wheels/torch-2.4.0.whl")
→ {"bytes": 198234112, "chunks": 24, "sha256": "…"}
```

ファイルは 8 MiB のチャンクに分割され、個別に暗号化されて転送ごとの prefix に置かれます。ファイルサイズに関係なくピークメモリは約 16 MB です。受信側は同じディレクトリの一時ファイルに組み立て、SHA-256 が一致してから rename します。中断しても、完全に見える不完全なファイルが残ることはありません。チャンクは成功時も失敗時も削除されます。

コマンドとは異なり、転送は at-most-once では**ありません**。バイトのコピーには副作用がないため、失敗した転送はそのまま再試行して安全です。

## 運用上の性質

以下の動作は、従来のリモートシェルとは意図的に異なります。

**タイムアウトはコマンドが実行されなかったことを意味しません。** 配送は at-most-once です。エージェントが実行を終えた後、応答のアップロードに失敗した可能性があります。副作用のある操作を再試行する前に、読み取り専用のコマンドで既に起きていないか確認してください。失われた応答が `recent_errors` に現れるのは、まさにこのためです。

**遅延は実在しますが小さいものです。** エージェントは稼働中 200 ms ごと、アイドル時は 5 秒までバックオフしてポーリングします。アイドル状態のエージェントへ送ったコマンドは数秒待つことがあります。

**エージェントの追加には再起動が必要です。** `allowed_agents` は起動時に一度だけ読まれます。そこに無いエージェントは、どれだけ健全でも見えません。

## 設定

TOML ファイルと環境変数の 2 系統で、**環境変数が常に優先**されます。

```toml
[s3]
endpoint = "https://cn-sy1.rains3.com"
bucket   = "my-relay-bucket"
prefix   = "relay-prod/"

[agent]
id = "legacy-01"
allow_any_path    = true
allow_any_program = true
```

秘密情報はファイルに置けます——その場合はファイルのパーミッションだけが保護になるため、秘密を含む設定が `0600` より緩いと起動時に警告が出ます。未知のキーはエラーとして扱われます。そうしないと `allowed_programs` の綴り誤りが許可リストを黙って空にしてしまいます。

[`relay.toml.example`](../relay.toml.example) を参照してください。

Skills は、曖昧なタイムアウト、長時間ジョブの分離実行、コンテキストを消費しないファイル転送など、ツールスキーマだけでは十分に表現できない運用上の判断基準を提供します。

## 仕組み

**ドアベル。** prefix の一覧取得は、アイドル中のエージェントが行う最も高価なリクエストです。コントローラーはコマンド投入後に単一のドアベルオブジェクトを上書きし、エージェントはそのキーへ HEAD するだけで、ETag が変わったときだけ一覧を取ります。定期的な全走査が、ドアベルを取りこぼした場合を拾います。

**適応的ポーリング。** 稼働中は 200 ms、アイドル時は 5 秒までバックオフし、仕事が来た瞬間に最速へ戻ります。Claude の呼び出しはバースト的であり、この形が合っています。

**ハートビートは独立したタスク**で送ります。これは意図的です。コマンドは直列に実行され数時間かかることがあり、同じループを共有するとハートビートが失効して、忙しいエージェントが停止しているように見えてしまいます。

**キー構成。** `cmd/<agent>/`、`resp/<agent>/`、`agents/<agent>.json`、`doorbell/<agent>.json`、`blob/<agent>/<transfer>/`。

## ストレージ側の要件

一時的な転送を成立させるには、以下のバケット設定が必要です。

1. 専用バケットまたは専用 prefix。バージョニングと Object Lock は**無効**に。有効だと削除が delete marker を作るだけになります。
2. 障害時の保険として、短いライフサイクルルールを設定します。
3. レプリケーション、アーカイブ、ペイロードを含むアクセスログは使いません。
4. サーバーサイド暗号化は併用して構いませんが、エンドツーエンドの層を置き換えるものではありません。
5. バケットポリシーで TLS を強制し、コントローラーとエージェントには別々の ID を割り当てます。

「事業者が一時的な暗号文にすら触れてはならない」という要件であれば、オブジェクトストレージでは満たせません。監査されたインメモリのメッセージングを使ってください。クライアント側のコードで保証できる性質ではありません。
